## GLM 图片处理

[智谱官方模型文档](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash)确认 `glm-5.3-flash` 支持 `image_url`，可以传 HTTP(S) URL 或 Base64 Data URL。

实现为固定观察提示 + 单张可见图片 → 文本观察。视觉模型不收到任务目标、skill、rubric、隐藏测试或答案，不执行工具；GLM-5.1 收到文本观察继续求解。相同 inline 图片在同一求解进程内缓存，HTTP URL 因内容可能变化不缓存。空响应、截断或 API 失败不会被冒充成功解析。该转换同时用于 SkillLearnBench 的 `read_image` 和 SkillsBench 的 OpenHands 图片消息；未开启的 DeepSeek 分支保持原接口输入行为。

`GLM_VISION_MODEL=glm-5.3-flash`；`GLM_VISION_BASE_URL` / `GLM_VISION_API_KEY` 留空时继承对应 GLM 配置。若账户需要独立视觉端点，在目标机器 `.env` 中设置。当前没有做真实图片 API 探测，pilot 才能确认该账户的调用权限和实际兼容性。

`vision_usage` 保存模型、图片引用哈希、观察文本、返回 usage 和成功/失败状态。汇总新增 `vision_calls`、`vision_tokens`，并纳入总 token；这些调用数是逻辑图片解析调用，SDK 内部 HTTP 重试不是独立实验样本。缺失美元费用仍为未知。Native ledger 位于 `/logs/agent/vision_usage.jsonl`，随 BenchFlow agent 日志归档。

论文应将新配置标成 **GLM-5.1 + GLM-5.3-Flash vision tool**。这项辅助能力不同于旧 Table 2 的执行条件；GLM Direct Oracle 与历史 75.1 的差异同时混有视觉工具、运行种子数等影响，不能作为单独隔离 rubricator 效果的因果证据。DeepSeek 两组新跑的配对消融仍使用共同条件。

## SkillOpt 的实际执行预算

固定源码：[trainer.py](https://github.com/microsoft/SkillOpt/blob/84b36cd5564e8893569e50e37f02a81d10b55e27/skillopt/engine/trainer.py)。关键调用在初始 selection（约 1140 行）、训练 rollout（约 1264 行）、候选 selection（约 1576 行）。缓存命中或无有效编辑时可跳过候选验收。slow/meta update 当前关闭，内部 `eval_test=False`；测试只由外层统一执行。

每个家族只有一个训练实例，`train_size=batch_size=accumulation=1`，所以每 epoch 只有一个训练 step。当前 `num_epochs=3, sel_env_num=2`：

| 部分 | 每家族逻辑任务执行 |
|---|---:|
| 初始 skill 验收 | 2 |
| 三轮训练轨迹 | 3 × 1 = 3 |
| 三轮候选验收 | 最多 3 × 2 = 6 |
| 合计 | **5–11** |

两个模型 × 20 家族：最多 **440 次训练侧执行**；SkillOpt 独立测试为两个模型 × 80 实例 = **160 次**，合计最多 **600 次**，不含基础设施失败重试。`edit_budget=4→2` 是每次文本更新允许的编辑条数，不再乘一次 oracle 数量。已加入计数和硬性超额报错；若上游流程意外需要第 12 次，不会静默执行。

建议维持当前 3 轮预算：与 SkillLift 每家族最多 `1 + 3×3 + 2 = 12` 次执行同一量级。两者 oracle 次数并非完全相等，实际 token/时长仍单独报告。若降到 2 轮，上界是每家族 8 次，两模型节省最多 120 次任务执行；按每次 10 分钟估算，是 20 小时串行工作量，不能直接当成节省 20 小时墙钟时间。预算未擅自降档。

原论文给 SkillOpt 的标称预算是 `2 epochs × 4 steps × 4 rollouts = 32`。当前是适应 SkillLearnBench 每家族单训练实例的低预算协议，**不能称为原论文 32 次预算的完整复现**。测试实例不参与 selection，使用的都是训练实例的全新执行。

当前整个泛化实验（两模型、四方法）的独立 test 为 640 次；加上 SkillOpt 最多 440 次和 SkillLift 最多 480 次训练侧执行，无基础设施错误时上界为 **1560 次**。1440 可以作规划估计，不能当硬性执行次数。限流、视觉解析、容器首次构建及 DeepSeek Flash 的实际时延仍需要 pilot 测量，V4-Pro 的 15 分钟只能作估算依据。

正式实验的最坏情况计数（不含 pilot、基础设施重试和纯 LLM 调用）：

| 部分 | 无早停时上界 | 规划估计的性质 |
|---|---:|---|
| GLM Direct Oracle 消融 | 87 × 10 = 870 | 约 400 依赖较多 anchor/候选提前成功 |
| DeepSeek 两组训练与复测 | 87 × (12 + 10) + 87 × 2 × 2 = 2262 | 约 1100 同样依赖早停及有效候选数 |
| 两模型泛化 | 1560 | 原 1440 是估计，不是程序预算上限 |

这些是保守上界，不是要求全部跑满。不要为了命中规划数而挑题、挑试次或中途按成绩删减任务。

## 重试与恢复审计修正

- 新泛化 solver 在同一次对话的同一次 API 请求处重试，不重复已完成的 shell/tool 动作；429/连接错误/408/409/5xx 等暂时错误最多 8 次，指数退避带抖动，支持 Retry-After 秒数或 HTTP 日期。404、凭据错误、额度耗尽、1210/1301、上下文超长等不会靠循环盲试。
- 框架 LLM 的内层重试关闭，避免 8×5 的请求膨胀。SkillOpt 的 SDK、官方 generic retry loop 和外层包装也收敛到单个 HTTP 重试层，避免三层乘法。
- 每个逻辑 oracle 最多 3 次物理执行；SkillLift/Direct Oracle coordinator 的额外重试设为 1，统一由 TrainingOracle 控制。默认不在同一次批处理里再次整轮重启失败 job。修复原因后重发命令仍可续跑，保留全部失败成本。
- [OpenHands SDK v1.22.1](https://github.com/OpenHands/software-agent-sdk/blob/v1.22.1/openhands-sdk/openhands/sdk/llm/llm.py)原生就有包含 RateLimitError 的重试，默认最多 5 次、等待 8–64 秒；不能笼统地说 SkillsBench solver 完全没有限流重试。
- 修正 journal 半行恢复：先截掉崩溃留下的损坏尾行，再追加新记录，保证再次重启能看见后续完成的工作。中间记录损坏仍报错，避免丢失完成证据。

## WSL 两个模型分开执行

准备好依赖和 `.env` 后，在两个 WSL 终端分别执行：

```bash
# 终端 A：GLM pipeline，默认并发 4
bash experiments/revision2026/run_all.sh supplementary glm

# 终端 B：DeepSeek pipeline，默认并发 8
bash experiments/revision2026/run_all.sh supplementary deepseek
```

各自依次跑 pilot → generalization → ablation，分别写入 `runs/revision2026/glm/` 和 `runs/revision2026/deepseek/`。不会自动跑 Table 2 重建或 WildClaw。也可单独使用 `generalization --models glm` / `ablation --models deepseek` 等入口。

本次完成的是静态调用链审计、离线故障注入和打包验证。首次 WSL 仍须确认：容器里图片桥接实际安装且日志被收集、视觉端点真实返回成功、OpenHands/SkillOpt 真正跑通，以及中断续跑和成本归档。没有把这些尚未执行的检查写成已通过。
